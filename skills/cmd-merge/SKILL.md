---
name: cmd-merge
description: Commit code changes in the current Git worktree and merge its committed HEAD into the branch checked out in the repository's main worktree. Use when the user invokes `cmd-merge` or asks to commit and merge the current worktree into the main worktree.
---

Commit the current worktree's changes, then merge them locally into the repository's main worktree. Invoking this skill authorizes both operations; proceed without routine confirmation.

1. Identify the source worktree with `git rev-parse --show-toplevel` and locate the main worktree with `git worktree list --porcelain`. For a non-bare repository, the first worktree entry is the main worktree. Use the branch currently checked out there as the merge target; do not assume its name is `main` or `master`.
2. Read the applicable repository instructions. Inspect the source worktree's status, staged and unstaged diffs, and untracked files to determine the intended commit contents. Include changes, new files, and deletions belonging to the requested work; preserve unrelated changes and staging. An unrelated merge, rebase, or other unfinished Git operation must be reported rather than silently continued or aborted.
3. Run the repository's required checks appropriate to the changes, reusing successful results when the relevant code has not changed. Stage the intended files and commit with a meaningful message following repository conventions. If there are no pending intended changes, reuse the existing HEAD without creating an empty commit. Record the exact source commit with `git rev-parse HEAD`.
4. If the source is already the main worktree, skip the merge and proceed to verification and reporting. Otherwise, check that the main worktree has a clean index and working tree, no unfinished Git operation, and a checked-out branch. If it is blocked, report the concrete state and obtain the missing direction; preserve its existing changes rather than automatically stashing, committing, or discarding them.
5. Merge the recorded source commit with `git -C <main-worktree> merge --no-edit <source-commit>`, allowing Git's normal fast-forward behavior. Address the main worktree explicitly in all commands that modify it, and retain its currently checked-out branch.
6. Resolve merge conflicts when the task and repository context establish the intended result, preserving the intended behavior of both sides. Use the corresponding generation tools for generated files. Run the required checks affected by conflict resolution, then finish the merge normally. If a conflict requires a decision that cannot be inferred, report the conflicting paths, the specific missing decision, and the current merge state before asking the user.
7. Verify that the source commit is included in the main worktree's HEAD with `git -C <main-worktree> merge-base --is-ancestor <source-commit> HEAD`, and inspect its status for unresolved conflicts or an unfinished merge. Report the source commit, main worktree path and branch, resulting HEAD, and relevant check results. If anything remains blocked, state which operations completed and what remains.

Keep this operation local. Pushes, history rewriting, and deletion of branches or worktrees require a separate user request.
